# AGENTS.md

ASP.NET Core MVC (net10.0) risk-management app, "Risk Pulse". Single web project under `RiskPulse/`; repo root holds `RiskPulse.slnx` (tracked). No tests, no CI (`.github/workflows` is an empty placeholder). EF Core 10 + Npgsql 10 + PostgreSQL. Working modules: login/authz, Users/Roles/Units administration, SAQ + KRI template designers, Assessment wizard. Stubs: Dashboard, Submissions, Risk Register templates.

## Commands
- Build: `dotnet build` with `workdir` = `RiskPulse/` (also works from repo root via the slnx). Build is the ONLY automated verification — no tests, lint, or format step.
- Run: `dotnet run` → http://localhost:5021 (launch profile `https` adds https://localhost:7110), env `Development` (`Properties/launchSettings.json`). Requires a running PostgreSQL DB `sit` on localhost:5432 with the `riskpulse` schema seeded, or login will fail.
- EF: **no `Migrations/` folder** — no migrations exist. The schema is provisioned manually via `Database/Seed.sql` (live lines 1–35) against a pre-created DB. `dotnet ef database update` will not work until a migration is generated.
- `Database/Seed.sql`: only lines 1–35 are live (9 permissions, 2 roles, 1 unit, 1 test user). Line 39 onwards is a legacy SQL Server `dbo.tbl*` draft (bare DDL at line 40, block-commented after) that is NOT PostgreSQL-compatible — **never execute anything past line 35**.
- Test login: username `nipunmm` with ANY password — `AdAuthenticationService` is a dev stub that always validates `true`.

## Request pipeline & auth (`Program.cs`)
Pipeline order: `UseExceptionHandler("/Error/Index")` + `UseHsts` (dev only) → `UseHttpsRedirection` → `UseRouting` → `UseAuthentication` → `UseAuthorization` → `UseStatusCodePages` → `MapStaticAssets` → `MapControllerRoute` with default `{controller=Login}/{action=Index}/{id?}`.
- Cookie auth: 20-min sliding expiry, `LoginPath=/Login/Index`, `AccessDeniedPath=/Login/AccessDenied`, HttpOnly. Auth cookie claims: `Name`, `NameIdentifier` (int user Id), `Role`, `DefaultPage` (permission desc), `Unit`, plus one `Permission` claim per role permission. `DefaultPage` drives post-login redirect and the "Return to Home" buttons on AccessDenied/Error pages.
- **JSON enums are strings**: `AddJsonOptions` registers `JsonStringEnumConverter`, so enum properties bind/serialize as strings in JSON bodies (e.g. `{ status: "Draft" }` → `AssessmentStatus.Draft`). `[FromBody]` DTOs with enum members work because of this.
- **Every new service must be registered `AddScoped<X>()` in `Program.cs`** (the existing 9 are listed there); each permission needs an `AddPolicy($"Permission:{...}")` line.

## Architecture & layering (match this exactly)
- **Controllers** stay flat in `Controllers/` (file-scoped `namespace RiskPulse.Controllers`) — thin, 1:1 with the flat `Views/{ControllerName}/` folders; routes follow class names. See `SaqTemplatesController.cs` and `AssessmentController.cs` as the canonical examples.
- **Services** are grouped by application workflow: `Services/Login/` (`AdAuthenticationService` stub, `DbAuthorizationService`, `LoginOrchestratorService`, `PermissionCatalog`, `PermissionPageMapper`), `Services/Administration/` (`UsersService`, `RolesService`, `UnitsService`), `Services/Templates/` (`SaqTemplatesService`, `KriTemplatesService`), `Services/Assessment/` (`AssessmentService`). Stub pages (Dashboard, Submissions, Risk Register, Error) have no service.
- **Models** are split by layer: `Models/Dto/` (data between layers/systems: `ApiResponse<T>`, `LoginRequestDto`, `LoginResultDto`, `*SaveDto`, `DeleteRequestDto`, `SaveResultDto`, `UserAuthorizationDto`) and `Models/ViewModel/` (data shaped for a view: `*IndexViewModel`, `*GridRowViewModel`, `*OptionViewModel`, `ErrorViewModel`). `Models/Enum/` holds the enums. `Views/` stays flat.
- **Entities** live in `Data/Entries/` as a flat 1:1 mirror of `riskpulse.*` tables (no domain grouping — `User`/`Role`/`Permission`/`Unit` serve both Login and Administration). Helpers in `Data/Extensions/DbSetExtensions.cs`: `EnsureUniqueAsync` (duplicate check → `InvalidOperationException`) and `ToOptionListAsync` (query → `List<OptionViewModel>`).

## Database & EF
- PostgreSQL schema `riskpulse` — set via `HasDefaultSchema("riskpulse")` in `Data/AppDbContext.cs` AND `Search Path=riskpulse` in the connection string.
- Connection string is hard-coded and COMMITTED in `appsettings.json` (`Server=localhost;Port=5432;Database=sit;User Id=postgres;Password=123456`) — known security debt (PROJECT-ANALYSIS.md §8); do not add further secrets.
- **Enums are persisted as `varchar(32)`** — every new enum-valued entity property requires `HasConversion<string>()` + `HasMaxLength(32)` in `AppDbContext.OnModelCreating`, plus a `DbSet<T>` property. All relationship/delete-behavior config is done there too.
- FK conventions already encoded: `SaqHeader`/`KriHeader` → `Group`/`Unit` **Restrict** (exactly one of GroupId/UnitId must be set — enforced as a business rule in the service); header → child items **Cascade**; `Kri` → `KriThresholdGroup` Restrict; `AssessmentHeader` → Saq/Kri Restrict and → `ScheduleHeader` Cascade; `UnitGroup` join is a unique `(GroupId, UnitId)` index.
- **timestamptz gotcha**: `ScheduleHeader.StartDate/EndDate` are `timestamptz` and Npgsql rejects `DateTimeKind.Unspecified`; the JSON binder yields Unspecified, so call `DateTime.SpecifyKind(value, DateTimeKind.Utc)` before saving (see `AssessmentService.UpsertScheduleAsync`).

## Backend recipe — add a CRUD feature (match the existing modules)
1. Entity in `Data/Entries/` + `DbSet` + enum→string mapping in `OnModelCreating`.
2. `*SaveDto` (+ reuse `DeleteRequestDto`) in `Models/Dto/` — DataAnnotations are the server-side source of truth (`[Required]`, `[RegularExpression]`, `[Range(1, int.MaxValue, ...)]` for FK ids). Convention: `Id == 0` means "new".
3. Service in the right `Services/` subfolder: grid methods project `*GridRowViewModel` with `AsNoTracking()`; Save/Delete methods validate, throw `InvalidOperationException` with user-facing messages (duplicate checks via `EnsureUniqueAsync`, locked-template guards, etc.); Save returns `SaveResultDto`.
4. Controller: `[Authorize(Policy = $"Permission:{PermissionCatalog.X}")]`; `GET Grid` → `Json(ApiResponse.Ok(rows))`; `POST Save/Delete` → `ControllerHelpers.TrySave(...)` / `ControllerHelpers.TryDelete(...)` (these null-guard, validate ModelState, run in `TryExecute`, and return `ApiResponse.Fail(ex.Message)` on `InvalidOperationException`). Use `TryExecute` directly for non-CRUD actions. **Never put business rules in controllers.** Register the service in `Program.cs`.
5. View: `Index.cshtml` with `@section Styles` (DataTables CSS) and `@section Scripts` (DataTables JS + inline IIFE). Initial dropdown data is injected server-side via `@Html.Raw(Json.Serialize(...))` (not AJAX). `_ViewImports.cshtml` imports `RiskPulse.Services.Login`, so `PermissionCatalog` is usable directly in any view.

## Permissions (single source of truth)
- `PermissionCatalog` strings drive the policies in `Program.cs` (`Permission:<name>`), `[Authorize]`, sidebar `User.HasClaim("Permission", ...)`, and `PermissionPageMapper`. They must match the DB `Permissions.PermissionDesc` seed rows and the `Permission` claims built in `LoginOrchestratorService` exactly. One value contains a space: `"Risk Register"`.
- `PermissionPageMapper.GetRouteForPermission(desc)` maps desc → `(controller, action)`: Dashboard, Submissions, Assessment, Users, Roles, Units, Saq→SaqTemplates, Kri→KriTemplates, RiskRegister→RiskRegisterTemplates; default = Dashboard.
- Renaming a page-backed permission means updating `PermissionCatalog`, the `Program.cs` policy, `PermissionPageMapper`, the seed, the controller, its view folder, and the sidebar link in `_Layout.cshtml`. Renaming a data-only permission (e.g. a new one with no page) skips the controller/view/sidebar part.
- `AdAuthenticationService` is a stub that always validates `true` — dev only, not real auth.

## Frontend conventions
- **Shared JS module** `wwwroot/js/modules/riskpulse.js` (loaded from `_Layout`) is the single home for cross-page helpers under `RiskPulse.*`: `toastSuccess`/`toastError`/`toastGenericError`, `postJson`/`getJson` (auto generic-error toast, routes `ApiResponse.success`; optional 4th arg `$trigger` disables during flight; optional `handlers.complete` runs after every outcome for button-label restoration), `serializeForm` (checkbox booleans + numeric coercion), `populateSelect` (accepts optional `placeholderValue`/`placeholderLabel`; items may carry optional `color` (hex) or `kind` (pill kind) which become `data-color`/`data-kind` on the options; auto-refreshes an enhanced select via `change.select2`), `initSelect2(selector)` (rp-themed select2 enhancement; auto-runs on all `select.rp-input` at ready; call explicitly for dynamically created selects AFTER insertion into the DOM), `showModal`/`hideModal`, `confirmDelete` (Swal), `initGrid` (DataTables defaults `pageLength:10`/`lengthMenu:[10,25,50]`), `escapeHtml`, `pill(label, kind, icon?)` (`rp-pill rp-pill-{kind}`, optional icon prepends a FontAwesome icon), `statusPill` (maps Active→success, Locked→warning, Draft→neutral, else→neutral), `statusKind(status)` (the RAG mapping alone — Active→success, Locked→warning, else→neutral; use it to tag status `<option>`s with `kind`), `validationError($el, message)` (toast + red `.rp-input-error` highlight + focus, auto-clears on the field's first input/change; pass `null` for rules with no single field; for enhanced selects the error lands on the visible `.select2-container--rp` wrapper), `clearFieldErrors($form)` (strip `.rp-input-error` from all fields — call in modal reset/show handlers). The `Toast` Swal mixin lives in the module — do not re-declare it in views. **Never re-implement these inline; `$.ajax` appears in views only via the module.** Views must NOT manually disable `$trigger` before calling `postJson`/`getJson` — the module owns the flight lock.
- **View scripts** are `@section Scripts` inline IIFEs that keep ONLY validation rules, DataTables column configs, and event wiring, with `/* ====== SECTION n — ... ====== */` banners. DataTables `columns` `data:` names (camelCase) must match the `*GridRowViewModel` JSON keys exactly. Grid action buttons carry `edit-{entity}-btn`/`delete-{entity}-btn` classes and are wired with delegated `$('#{table} tbody').on('click', ...)`.
- **Modals**: open/close programmatically via `RiskPulse.showModal(id)` / `RiskPulse.hideModal(formEl)` — the vendored bundle is Bootstrap 5, which has no jQuery `.modal()` API. Never use `$('#x').modal('show')` or raw `bootstrap.Modal.getOrCreateInstance` outside the module.
- **Dropdowns (select2)**: every `<select class="rp-input">` is enhanced by the vendored select2 4.1 with the first-party theme `select2-container--rp` (styled in `site.css` to mirror `.rp-input`: same border/radius/type/focus ring + native chevron). Search box appears only at ≥10 options (`minimumResultsForSearch: 10`); dropdowns inside modals attach to the modal (`dropdownParent`). Colored options opt in per option via `data-color="#hex"` (swatch square) or `data-kind="success|warning|danger|neutral"` (pill chip) — set them through `populateSelect` items or `.attr('data-color', ...)` before `initSelect2`. Never call `$el.select2(...)` directly in views — always go through `RiskPulse.initSelect2`. After direct DOM option manipulation outside `populateSelect`, fire `$select.trigger('change.select2')` to refresh the display without triggering app handlers.
- **Styling**: design-system classes in `wwwroot/css/site.css` (`rp-btn-primary`, `rp-btn-secondary`, `rp-btn-edit`, `rp-btn-delete`, `rp-pill-success`/`warning`/`danger`/`neutral`, `rp-input`, `rp-card`, `rp-table`). All RiskPulse-authored classes use the `rp-` prefix. Selects use `rp-input` (never `rp-input form-select`). Grid action buttons use `rp-btn-edit`/`rp-btn-delete`, not `rp-btn-secondary`.
- **Layout shell polish**: sidebar uses layered tonal gradient (tokens `--sidebar-grad-top/bottom`) + a `.rp-sidebar-brand-icon::after` sonar ring (7s, paused under `html[data-sidebar="collapsed"]`); nav hover = `--sidebar-teal-wash`, active = teal gradient + `inset 3px 0` teal rail (`--sidebar-active-rail`). Sidebar toggle icon is `fa-chevron-right` → rotates 90° to down via `transform: rotate(90deg)` on expand. Topbar is frosted glass (`--topbar-glass` + `backdrop-filter: blur(8px)`, `@supports` fallback) with a user profile section (gradient avatar, username, role) and a logout link. Page canvas = `--page-bg-grad` + `.rp-bg-pattern` + `.rp-main-ambient` (breathing teal glow). Entrance: `rp-shell-fade` (sidebar), `rp-topbar-rise` (topbar), `rp-page-fade` (content) — one-time per load, staggered 0.1s→0.15s→0.25s. These match the Login page's craft language. `prefers-reduced-motion` disables all shell and login animations.
- **Standalone pages** (`Login/Index`, `Login/AccessDenied`, `Error/Index`) set `Layout = null` and render full HTML with only `site.css` + FontAwesome; `Login/Index` additionally loads jquery + sweetalert2 + riskpulse.js (no Bootstrap bundle — don't call modal helpers there; uses `RiskPulse.postJson()` + `RiskPulse.toastError()` + `handlers.complete` for button-label restore). `_Layout.cshtml` loads bootstrap, sweetalert2, select2, `js/site.js` (sidebar logic), and the module.
- **Vendored libs currently in `wwwroot/lib/`: bootstrap, datatables, font-awesome, jquery, select2, sweetalert2.** Selects are enhanced by select2 with the first-party `select2-container--rp` theme — see "Dropdowns (select2)" above; don't restyle selects outside that theme block in `site.css`.
- **Wizard** (`Views/Assessment/Wizard.cshtml` + `_StepName|Saq|Kri|Schedule|Finalize.cshtml` partials): step bar with `data-step="1..5"` (plus a locked `data-step="rr"` Risk Register step); panels are `.rp-wizard-panel[data-step=n]`; a JS `state` object tracks `completed`/`frontier`; each step persists via its own AJAX endpoint (SaveName/SaveSaq/SaveKri/SaveSchedule) then advances; step 5 posts `Finalize` with `status: 'Draft' | 'Active'`.

## Code conventions
- `Models/Dto/*`, `Models/ViewModel/*`, and `Data/Entries/*` use block namespaces (`namespace X { }`); controllers/services use file-scoped namespaces. Follow the folder you are editing.
- **Comments**: `// --- Section name ---` banners in controllers/services to identify action/method groups. Don't comment property-bag classes (entities, DTOs, view models). Views keep their `/* ====== SECTION n — ... ====== */` style.
- Git: lowercase conventional prefixes for commits/branches (`feat/...`, `fix/...`, `refactor/...`). Commit only when asked.
