# AGENTS.md

ASP.NET Core MVC (net10.0) risk-management app, "Risk Pulse". Single web project under `RiskPulse/`; repo root holds `RiskPulse.slnx` (tracked). No tests, no CI (`.github/workflows` is an empty placeholder). EF Core 10 + Npgsql 10 + PostgreSQL.

> **Scope of this file:** the technical rules and code patterns to follow when working in this codebase (stack, request pipeline, layering, EF/entity conventions, CRUD recipe, frontend conventions). It deliberately does **not** describe individual pages/features — for what each page or feature does, and its status, see `RiskPulse/AI/spec.md`, the source of truth for features.

## Commands
- Build: `dotnet build` with `workdir` = `RiskPulse/` (also works from repo root via the slnx). Build is the ONLY automated verification — no tests, lint, or format step.
- Run: `dotnet run` → http://localhost:5021 (launch profile `https` adds https://localhost:7110), env `Development` (`Properties/launchSettings.json`). Requires a running PostgreSQL DB `sit` on localhost:5432 with the `riskpulse` schema seeded, or login will fail.
- EF: `Migrations/` **exists on disk but is git-ignored** via `.gitignore` `**/Migrations/`, so migrations are not committed. `dotnet ef` (global tool v10) **is** available and the initial migration `20260929191413_xxx` is applied to `sit`; newer schema changes are added as new migrations and pushed with `dotnet ef database update` (e.g. `20261011093848_AddAssessmentHeaderPeriodUniqueIndex`). A seed script **does** exist at `Data/Seed.sql` (schema ALTERs, permissions/roles/unit/users, and the two workflow step dictionaries); a fresh DB must still be provisioned with the schema + `Data/Seed.sql`.
- Test login: username `nipunmm` with ANY password — `AdAuthenticationService` is a dev stub that always validates `true`.

## Request pipeline & auth (`Program.cs`)
Pipeline order: `UseExceptionHandler("/Error/Index")` + `UseHsts` (dev only) → `UseHttpsRedirection` → `UseRouting` → `UseAuthentication` → `UseAuthorization` → `UseStatusCodePages` → `MapStaticAssets` → `MapControllerRoute` with default `{controller=Login}/{action=Index}/{id?}`.
- Cookie auth: 20-min sliding expiry, `LoginPath=/Login/Index`, `AccessDeniedPath=/Login/AccessDenied`, HttpOnly. Auth cookie claims: `Name`, `NameIdentifier` (int user Id), `Role`, `DefaultPage` (permission desc), `Unit`, plus one `Permission` claim per role permission. `DefaultPage` drives post-login redirect and the "Return to Home" buttons on AccessDenied/Error pages.
- **JSON enums are strings**: `AddJsonOptions` registers `JsonStringEnumConverter`, so enum properties bind/serialize as strings in JSON bodies (e.g. `{ status: "Draft" }` → `AssessmentActivationStatus.Draft`). `[FromBody]` DTOs with enum members work because of this.
- **Every new service must be registered `AddScoped<X>()` in `Program.cs`** (the existing scoped services are listed there); each permission needs an `AddPolicy($"Permission:{...}")` line. (Background work is registered with `AddHostedService<X>()`; the former recurring-period hosted service was removed with the recurring scheduler.)

## Architecture & layering (match this exactly)
- **Controllers** stay flat in `Controllers/` (file-scoped `namespace RiskPulse.Controllers`) — thin, 1:1 with the flat `Views/{ControllerName}/` folders; routes follow class names. See `SaqTemplatesController.cs` and `AssessmentController.cs` as the canonical examples.
- **Services** are grouped by application workflow: `Services/Login/` (`AdAuthenticationService` stub, `DbAuthorizationService`, `LoginOrchestratorService`, `PermissionCatalog`, `PermissionPageMapper`), `Services/Administration/` (`UsersService`, `RolesService`, `UnitsService`), `Services/Templates/` (`SaqTemplatesService`, `KriTemplatesService`, `AssessmentTemplatesService`), `Services/Assessment/` (`AssessmentActivationService` — the activation grid + create/edit modal, `AssessmentService` — snapshots the real assessment from the template, `SubmissionsService`, `WorkflowStepCodes`), `Services/Dashboard/` (`DashboardService`), `Services/Monitoring/` (`MonitorService` — the cross-unit status matrix), `Services/Utilities/` (`CodeGeneratorService`). Stub pages (Risk Register, Error) have no service.
- **Models** are split by layer: `Models/Dto/` (data between layers/systems: `ApiResponse<T>`, `LoginRequestDto`, `LoginResultDto`, `*SaveDto`, `DeleteRequestDto`, `SaveResultDto`, `UserAuthorizationDto`) and `Models/ViewModel/` (data shaped for a view: `*IndexViewModel`, `*GridRowViewModel`, `*OptionViewModel`, `ErrorViewModel`). `Models/Enum/` holds the enums. `Views/` stays flat.
- **Entities** live in `Data/Entries/` as a flat 1:1 mirror of `riskpulse.*` tables (no domain grouping — `User`/`Role`/`Permission`/`Unit` serve both Login and Administration). Helpers in `Data/Extensions/DbSetExtensions.cs`: `EnsureUniqueAsync` (duplicate check → `InvalidOperationException`) and `ToOptionListAsync` (query → `List<OptionViewModel>`).

## Database & EF
- PostgreSQL schema `riskpulse` — set via `HasDefaultSchema("riskpulse")` in `Data/AppDbContext.cs` AND `Search Path=riskpulse` in the connection string.
- Connection string is hard-coded and COMMITTED in `appsettings.json` (`Server=localhost;Port=5432;Database=sit;User Id=postgres;Password=123456`) — known security debt; do not add further secrets.
- **Enums are persisted as `varchar(32)`** — every new enum-valued entity property requires `HasConversion<string>()` + `HasMaxLength(32)` in `AppDbContext.OnModelCreating`, plus a `DbSet<T>` property. All relationship/delete-behavior config is done there too.
- FK conventions already encoded: `SaqHeader`/`KriHeader` → `Group`/`Unit` **Restrict** (exactly one of GroupId/UnitId must be set — enforced as a business rule in the service); header → child items **Cascade**; `AssessmentTemplateItem`/`AssessmentItem` are **polymorphic** (`ItemType` `Saq`/`Kri` + `ItemId`, no FK) → owning root **Cascade**; `AssessmentTemplate` ← `AssessmentActivation` **Restrict** (an activation optionally points at one template); `AssessmentActivation` → `AssessmentHeader` **Restrict** → `AssessmentUnit` → `AssessmentItem` **Cascade**, workflow/user FKs **Restrict**; answers/values → item **Cascade**, question/option/kri FKs **Restrict**; `Workflow` → `WorkflowStep` **Cascade**; `UnitGroup` join is a unique `(GroupId, UnitId)` index.
- **Statuses are DB-driven, not enums**: assessment/submission state comes from `WorkflowStep.StepCode` rows of the `ASSESSMENT-UNIT` and `ASSESSMENT-ITEM` workflows. The step-code string literals live in one place — `Services/Assessment/WorkflowStepCodes.cs` — and must match the `Data/Seed.sql` seed; `SubmissionsService`/`DashboardService` reference it. `AssessmentStatus` (`Pending`) is written once at assessment creation and never read for logic — do not add logic keyed on it.
- **Assessment snapshot flow**: `AssessmentActivationService.FinalizeAsync` → `AssessmentService.CreateAssessmentAsync` snapshots the real assessment from the activation's Assessment Template (`AssessmentHeader` → one `AssessmentUnit` per targeted unit → one `AssessmentItem` per template item, all at the workflows' `IsInitial` step). One-time only; the former recurring generator/hosted service/`SyncNow`/`Close` were removed.
- **timestamptz gotcha**: `AssessmentActivation.StartDate/EndDate/StartMonth` are `timestamptz` and Npgsql rejects `DateTimeKind.Unspecified`; the JSON binder yields Unspecified, so call `DateTime.SpecifyKind(value, DateTimeKind.Utc)` before saving (see `AssessmentActivationService.CreateOrUpdateAsync`).
- **Template codes**: `SaqHeader.SaqCode`/`KriHeader.KriCode`/`AssessmentTemplate.AssessmentTemplateCode`/`AssessmentHeader.AssessmentCode`/`AssessmentActivation.ActivationCode` are unique generated keys (`{SAQ|KRI|AST|ASM|ACT}-yyyyMMdd-0001`) issued by `CodeGeneratorService`. KRI items carry flat `GreenLimit`/`AmberLimit`/`RedLimit` ints (the old threshold-config subsystem was removed) — RAG is computed in code (`KriEntry.cshtml`, `DashboardService`).

## Backend recipe — add a CRUD feature (match the existing modules)
1. Entity in `Data/Entries/` + `DbSet` + enum→string mapping in `OnModelCreating`.
2. `*SaveDto` (+ reuse `DeleteRequestDto`) in `Models/Dto/` — DataAnnotations are the server-side source of truth (`[Required]`, `[RegularExpression]`, `[Range(1, int.MaxValue, ...)]` for FK ids). Convention: `Id == 0` means "new".
3. Service in the right `Services/` subfolder: grid methods project `*GridRowViewModel` with `AsNoTracking()`; Save/Delete methods validate, throw `InvalidOperationException` with user-facing messages (duplicate checks via `EnsureUniqueAsync`, locked-template guards, etc.); Save returns `SaveResultDto`.
4. Controller: `[Authorize(Policy = $"Permission:{PermissionCatalog.X}")]`; `GET Grid` → `Json(ApiResponse.Ok(rows))`; `POST Save/Delete` → `ControllerHelpers.TrySave(...)` / `ControllerHelpers.TryDelete(...)` (these null-guard, validate ModelState, run in `TryExecute`, and return `ApiResponse.Fail(ex.Message)` on `InvalidOperationException`). Use `TryExecute` directly for non-CRUD actions. **Never put business rules in controllers.** Register the service in `Program.cs`.
5. View: `Index.cshtml` with `@section Styles` (DataTables CSS) and `@section Scripts` (DataTables JS + inline IIFE). Initial dropdown data is injected server-side via `@Html.Raw(Json.Serialize(...))` (not AJAX). `_ViewImports.cshtml` imports `RiskPulse.Services.Login`, so `PermissionCatalog` is usable directly in any view.

## Permissions (single source of truth)
- `PermissionCatalog` strings drive the policies in `Program.cs` (`Permission:<name>`), `[Authorize]`, nav `User.HasClaim("Permission", ...)`, and `PermissionPageMapper`. They must match the DB `Permissions.PermissionDesc` seed rows and the `Permission` claims built in `LoginOrchestratorService` exactly. Two values contain spaces: `"Assessment Activation"` and `"Risk Register"`.
- `PermissionPageMapper.GetRouteForPermission(desc)` maps desc → `(controller, action)`: Dashboard, Submissions, Assessment, Users, Roles, Units, Saq→SaqTemplates, Kri→KriTemplates, AssessmentTemplates→AssessmentTemplates, RiskRegister→RiskRegisterTemplates; default = Dashboard.
- Renaming a page-backed permission means updating `PermissionCatalog`, the `Program.cs` policy, `PermissionPageMapper`, the seed, the controller, its view folder, and the nav links in `_Layout.cshtml` (top nav) — the Dashboard has no sidebar, just the same nav. Renaming a data-only permission (e.g. a new one with no page) skips the controller/view/nav part.
- `AdAuthenticationService` is a stub that always validates `true` — dev only, not real auth.

## Frontend conventions
- **Shared JS module** `wwwroot/js/modules/riskpulse.js` (loaded from `_Layout`) is the single home for cross-page helpers under `RiskPulse.*`: `toastSuccess`/`toastError`/`toastGenericError` (**SweetAlert2 centered dialogs** — icon + title + OK button; buttons use SweetAlert's built-in styling recolored to the RP palette via Swal's CSS variables; the names are legacy, no toast pills anywhere), `postJson`/`getJson` (auto generic-error dialog, routes `ApiResponse.success`; optional 4th arg `$trigger` disables during flight; shows the shared `#rp-loading-overlay` for the whole request — opt out with `handlers.overlay === false`; optional `handlers.complete` runs after every outcome for button-label restoration), `showLoading`/`hideLoading` (the same overlay for non-transport flows), `serializeForm` (checkbox booleans + numeric coercion), `populateSelect` (accepts optional `placeholderValue`/`placeholderLabel`; items may carry optional `color` (hex) or `kind` (pill kind) which become `data-color`/`data-kind` on the options; auto-refreshes an enhanced select via `change.select2`), `initSelect2(selector)` (rp-themed select2 enhancement; auto-runs on all `select.rp-input` at ready; call explicitly for dynamically created selects AFTER insertion into the DOM), `showModal`/`hideModal`, `confirmDelete` (Swal — fixed title "Please Confirm", caller's question folded into the body, **Yes/No** buttons), `initGrid` (DataTables defaults **`paging:true` with `pageLength:10`** + page-size selector `lengthMenu:[10,25,50,'All']`, `lengthChange:true`, stock info line, and a compact `dom` (length left / search top-right, info left / pager right); `cfg` must still supply ajax/columns/order), `escapeHtml`, `pill(label, kind, icon?)` (`rp-pill rp-pill-{kind}`, optional icon prepends a FontAwesome icon), `statusPill` (maps Active→success, Locked→warning, Draft→neutral, else→neutral), `statusKind(status)` (the RAG mapping alone — Active→success, Locked→warning, else→neutral; use it to tag status `<option>`s with `kind`), `validationError($el, message)` (error dialog + red `.rp-input-error` highlight + focus, auto-clears on the field's first input/change; pass `null` for rules with no single field; for enhanced selects the error lands on the visible `.select2-container--rp` wrapper), `clearFieldErrors($form)` (strip `.rp-input-error` from all fields — call in modal reset/show handlers), `createChecklistPicker(cfg)` (compact searchable checkbox multi-select for dense modal/admin screens — pass `containerSel`/`options`/`selected`/`searchPlaceholder`/`emptyText`/`previewOpen(id, $trigger)`/`onSelectionChange(ids)`; returns `{ selectedIds, labels, setSelected, isChecked }`; used by Assessment Templates), `templatePreview(cfg)` (manages a read-only SAQ/KRI preview modal — pass `modalId`/`bodyId`/`labelId` + `saqUrl`/`kriUrl`; returns `{ openSaq, openKri }`; the host modal must be `modal-dialog-scrollable` and the renderer emits dense question/option/KRI rows + a count pill so long templates stay compact). The Swal helpers live in the module — do not re-declare them in views. **Never re-implement these inline; `$.ajax` appears in views only via the module.** Views must NOT manually disable `$trigger` before calling `postJson`/`getJson` — the module owns the flight lock.
- **View scripts** are `@section Scripts` inline IIFEs that keep ONLY validation rules, DataTables column configs, and event wiring, with `/* ====== SECTION n — ... ====== */` banners. DataTables `columns` `data:` names (camelCase) must match the `*GridRowViewModel` JSON keys exactly. Grid action buttons carry `edit-{entity}-btn`/`delete-{entity}-btn` classes and are wired with delegated `$('#{table} tbody').on('click', ...)`.
- **Modals**: open/close programmatically via `RiskPulse.showModal(id)` / `RiskPulse.hideModal(formEl)` — the vendored bundle is Bootstrap 5, which has no jQuery `.modal()` API. Never use `$('#x').modal('show')` or raw `bootstrap.Modal.getOrCreateInstance` outside the module.
- **Dropdowns (select2)**: every `<select class="rp-input">` is enhanced by the vendored select2 4.1 with the first-party theme `select2-container--rp` (styled in `site.css` to mirror `.rp-input`: same border/radius/type/focus ring + native chevron). Search box appears only at ≥10 options (`minimumResultsForSearch: 10`); dropdowns inside modals attach to the modal (`dropdownParent`). Colored options opt in per option via `data-color="#hex"` (swatch square) or `data-kind="success|warning|danger|neutral"` (pill chip) — set them through `populateSelect` items or `.attr('data-color', ...)` before `initSelect2`. Never call `$el.select2(...)` directly in views — always go through `RiskPulse.initSelect2`. After direct DOM option manipulation outside `populateSelect`, fire `$select.trigger('change.select2')` to refresh the display without triggering app handlers.
- **Unit picker**: selecting many units (Unit Groups add/edit) uses a `.rp-unit-picker` checkbox list, not a tagging multi-select — a search field, Select all / Clear `.rp-unit-mini-btn`s, a scrollable `.rp-unit-list` of `.rp-unit-option` rows (checkbox + name + unit-type `pill`), and a live `.rp-unit-count` (`ok` at ≥2, `warn` otherwise). Built by the in-view `createUnitPicker(pickerId, countId)` helper in `Views/Units/Index.cshtml`; the payload reads `$form.find('.rp-unit-picker').data('picker').getIds()`. Unit options come from `UnitsService.GetAllUnitsAsync` as `OptionViewModel` items carrying `type` = unit type (`Branch`/`Department`).
- **Styling**: design-system classes in `wwwroot/css/site.css` (`rp-btn-primary`, `rp-btn-secondary`, `rp-btn-edit`, `rp-btn-delete`, `rp-pill-success`/`warning`/`danger`/`info`/`violet`/`neutral`, `rp-input`, `rp-card`, `rp-table`). All RiskPulse-authored classes use the `rp-` prefix. Theme is **hybrid Siyapatha (Sapphire Glass Edition)**: dark sapphire/cyan glass chrome (nav, heroes, login, overlays) over light content; the primary action (`rp-btn-primary`) is a **Siyapatha-orange glass** button (`--orange #f58220`) whose label is **`--navy-deep #0a192f`, never white** (AA), with a `rgb(from var(--orange-deep) r g b / .5)` rim and a `--orange-deep` pressed state. Tokens follow `AI/DESIGN.md` v2 — chrome `--navy-deep`/`--navy-mid`/`--ink-raised`/`--steel`/`--steel-deep`/`--steel-wash` (`--steel #38bdf8` is **dark-chrome only** — fails 3:1 on light; use `--steel-deep #0369a1`); action `--orange`/`--orange-hover-start`/`--orange-hover-end`/`--orange-deep`/`--orange-wash`; on-light accent and focus ring `--focus #0284c7`; `--form-border #0284c7` for every control boundary; semantic `--success` is **teal-green `#047857`**, `--warning #b45309`/`--warning-text #92400e`, `--error #b91c1c`/`--error-bright #ef4444`, `--info #0369a1`, `--violet #7c3aed`, `--neutral`, each with a `-wash` bg + `-border` hairline (3-step wash); `--chart-1..6` + `--seq-1..5`. Legacy v1 names (`--blue*`, `--indigo`, `--glass-tint`, `--focus-border`, `--purple*`, `--text-faint`, `--amber`, `--*-bg`) are removed — do not reintroduce. No hard-coded colors in rules: use `rgb(from var(--steel) r g b / .x)` or the `--*-rgb` triplets. Glass surfaces use `.rp-glass-dark`/`.rp-glass-light`/`.rp-glass-card` (aliases `.glass-dark`/`.glass-light`). Selects use `rp-input` (never `rp-input form-select`). Grid action buttons use `rp-btn-edit`/`rp-btn-delete`, not `rp-btn-secondary`.
- **Layout shell (top nav)**: `_Layout.cshtml` renders a sticky ink/steel glass top nav (`.rp-topnav` → `.rp-topnav-inner`: brand, `.rp-nav` links, Templates/Administration Bootstrap dropdowns styled as `.rp-nav-menu`, `.rp-nav-right` user chip + logout) and a leading `.rp-skip-link` (reveals on focus → `#main-content`). `js/site.js` only handles the ≤991px nav drawer (`#rpNavToggle`/`#rpNav`) — no sidebar, no localStorage state. Page canvas = `--page-bg` + `--page-glow` + `.rp-bg-pattern` + `.rp-main-ambient` (breathing glow), content in `.rp-page` (max 1320px) + slim `.rp-footer`. Entrance: `rp-shell-fade` (nav), `rp-topbar-rise`, `rp-page-fade` — one-time per load. `prefers-reduced-motion` disables all shell and login animations. Interactive targets use `--target-min: 44px`; focus is always visible (2px ring — `--focus` on light, `--focus-on-dark` on dark chrome).
- **Page headers**: every module view opens with a `.rp-hero` banner (`rp-hero--ink|blue|violet|teal|slate|green|orange|gold` per module — common ink base + a module-tinted radial glow) containing `<h1 class="rp-display-lg">` + `.rp-hero-sub`, the primary action in `.rp-hero-actions` (top-right), back links as `.rp-hero-back`. Never use `rp-page-header` (legacy, styled only as fallback). Grid tables are always `<div class="table-responsive">`-wrapped inside the card.
- **Dashboard** uses the standard top-nav shell like every other page (no "Shell" ViewData, no left sidebar); its `.rp-hero--ink` hero and KPI/status/KRI/attention/history cards are **server-rendered**, not DataTables.
- **Standalone pages** (`Login/Index`, `Login/AccessDenied`, `Error/Index`) set `Layout = null` and render full HTML with only `site.css` + FontAwesome; `Login/Index` is the two-column `.rp-login-shell` (ink/steel glass brand panel + `.rp-login-panel` card) and additionally loads jquery + sweetalert2 + riskpulse.js (no Bootstrap bundle — don't call modal helpers there; sign-in errors show as a `RiskPulse.toastError()` dialog; `handlers.complete` restores the button label). `_Layout.cshtml` loads bootstrap, sweetalert2, select2, `js/site.js` (top-nav drawer logic), and the module.
- **Vendored libs currently in `wwwroot/lib/`: bootstrap, datatables, font-awesome, jquery, select2, sweetalert2.** Selects are enhanced by select2 with the first-party `select2-container--rp` theme — see "Dropdowns (select2)" above; don't restyle selects outside that theme block in `site.css`.

## Code conventions
- `Models/Dto/*`, `Models/ViewModel/*`, and `Data/Entries/*` use block namespaces (`namespace X { }`); controllers/services use file-scoped namespaces. Follow the folder you are editing.
- **Comments**: `// --- Section name ---` banners in controllers/services to identify action/method groups. Don't comment property-bag classes (entities, DTOs, view models). Views keep their `/* ====== SECTION n — ... ====== */` style.
- Git: lowercase conventional prefixes for commits/branches (`feat/...`, `fix/...`, `refactor/...`). Commit only when asked.
